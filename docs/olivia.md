Olivia on Etapel uses a dedicated Olivia 3.6.0 engine and PostgreSQL database on the VPS, with the existing `etapel` tenant and service account. The shared site layout loads the floating chat on every page in Spanish, English, German, Italian, French and Brazilian Portuguese. The website and gateway accept `es`, `en`, `de`, `it`, `fr` and `pt`. Replies follow the visitor's message or explicit language request; the page language is a fallback for ambiguous messages without an established conversation language. The proxy accepts requests from both public Etapel domains and the configured Vercel deployments.

Browser → `/api/olivia` (Vercel function) → authenticated `/etapel/chat` gateway on `https://olivia.o7digitalgroup.com` → private `etapel-olivia36:8093/v1/chat`.

Vercel stores `OLIVIA_GATEWAY_KEY` server-side. The gateway runs from `/opt/o7/apps/etapel-olivia` on `o7-vps`, using `infrastructure/olivia/compose.yaml`. Its existing private `.env` contains `GATEWAY_KEY`, `OLIVIA_EMAIL` and `OLIVIA_PASSWORD`; never commit it. The exact public ingress route stays `/etapel/chat`. The gateway joins only the proxy network and the dedicated Etapel engine network. Neither the engine nor its database publishes a host port.

The engine runs from `/opt/o7/apps/etapel-olivia36`, using `infrastructure/olivia/engine/compose.yaml`. `source.json` pins the actual Olivia 3.6 source repository and commit. The image reuses the existing Olivia base image's Python dependencies, replaces its application with that pinned 3.6 source, and checks the installed requirements. Its private `.env` preserves Etapel's current provider/model settings and uses new database, JWT and vault secrets. `.env.db` contains only the dedicated database credentials. `prepare.py` creates these files on the VPS with mode 0600 and preserves existing credentials when rerun. Local-model fallback is disabled; the requested provider must answer successfully.

The site proxy fixes routing to `POWERFUL`; visitor-supplied routing and version fields are ignored. It accepts only a successful `3.6.0` / `POWERFUL` gateway response. The gateway verifies the engine's `/health` version, checks the requested routing and actual provider/model, signs conversation identifiers and limits messages per visitor IP. An older engine or downgraded response produces an unavailable response rather than a false version label. Authenticated older site proxies that omit routing still default to `FAST` at the gateway.

Every website build generates `/.well-known/etapel-knowledge.json` after CMS edits and localization. It contains all built canonical pages in every language: complete main copy, technical specifications, catalogue summaries, public form guidance and useful links. Administration, chat transcripts and input values are excluded. Repeated product grids are attached to each product's own document. The gateway's `site-knowledge.mjs` loads and validates this public index, refreshes it every minute and retrieves relevant pages for each message. The current page and the previous conversation's public topic keys help follow-up questions. Matching translations are accompanied by the Spanish original, which often has more detailed technical or legal content. Replies include source links and the public knowledge hash/page count for verification. A transient website outage retains the last validated index; without any valid index the request fails rather than using an outdated summary. The gateway has a 256 MB memory limit for this search index; no translation API or embeddings service is called while indexing.

`migrate-etapel.py` copies only records with `tenant_id = etapel` from the frozen central 3.5 database into an empty dedicated database. It preserves account IDs, password hashes, conversations, messages and audit history, checks counts and resets integer sequences. Payloads remain in memory and are never printed. The source is read only; existing destination data is rejected. Encrypted tenant secrets require a separate migration and cause this script to stop. The central engine and other tenants are not changed.

For a fresh deployment:

1. Create `/opt/o7/apps/etapel-olivia36/core` and copy the files from `infrastructure/olivia/engine/` into its parent directory.
2. From a local checkout of the source repository in `source.json`, export the pinned commit's `app`, `requirements.txt`, `tests` and `pytest.ini` with `git archive` into the VPS `core` directory. Do not export credentials, databases or local runtime files.
3. Run `python3 prepare.py` and `docker compose up -d --build --wait` in the engine directory. Verify `/health` reports `3.6.0` and test the provider before moving traffic. Engine tests must use a disposable SQLite database, deterministic embeddings, test-only authentication secrets and an empty external API key.
4. Back up the existing gateway files. Briefly stop only `etapel-olivia-gateway`, run `python3 /opt/o7/apps/etapel-olivia36/migrate-etapel.py`, install the updated gateway files, and start the gateway with `docker compose up -d --force-recreate --wait`. Preserve its existing `.env` so conversation signatures and service credentials remain valid.
5. Verify gateway health, real new chats and conversation follow-ups, then deploy the website proxy on Vercel. Check `/api/olivia` reports `version: 3.6.0` and `routing: POWERFUL` and test the widget in Spanish and English.

To roll back, first deploy the previous website proxy, then restore the backed-up gateway files and its former network connection. Keep both databases. Reconcile any conversations created after cutover before moving their traffic back; never delete the dedicated database to roll back.

The widget's contact form remains independent of the AI engine. Every successful AI reply automatically reveals the inline form with first name, last name, email, phone, preferred contact method and privacy consent, including replies to messages without commercial keywords. An already visible form keeps its entered values and focus. A failed AI request does not open the form; a completed contact submission does not reopen it. Clicking any Etapel SATA finder card opens Olivia with a dedicated spare-parts quote form: model, reference or part description, quantity and optional serial number. A separate link opens the official SATA finder in a new tab; SATA's `SAMEORIGIN` policy prevents embedding it in Etapel. Its Spanish, English, German, Italian and French pages are mapped explicitly; Portuguese uses the English finder while keeping the Etapel form in Portuguese. Modified clicks and links without JavaScript retain normal navigation to SATA. Etapel cannot read selections made on the separate SATA website.

Visitor submissions use the existing Etapel Formspree endpoint. The request includes the part details, originating page, language and recent chat context; success appears only after Formspree accepts it. Failed submissions retain the entered fields. Contact field values are sent only when the visitor submits the form, not to the AI endpoint. Browser conversation and form state last for the current page. Tool integrations remain subject to the engine's tenant policies and sandbox controls.

Publishing content through the Studio automatically rebuilds the public knowledge index. No manual knowledge-file synchronization is needed. Validate coverage with `docker exec etapel-olivia-gateway node -e 'fetch("http://localhost:3096/health").then(r=>r.json()).then(console.log)'` and compare its hash with the public index.

For this index-backed gateway, deploy the website and verify the public index first. Back up the gateway and Compose files, then copy `gateway.mjs`, `site-knowledge.mjs` and `compose.yaml` to `/opt/o7/apps/etapel-olivia/`. Run `docker compose up -d --force-recreate --wait gateway` there. Preserve `.env`, the engine and both databases. Verify gateway health, factual questions in all six languages, a language differing from the page and a signed conversation follow-up. No migration is needed.
